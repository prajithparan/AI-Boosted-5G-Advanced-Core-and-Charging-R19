## ADR-0148: gap-closure task #106 continuation -- UDR real Event Exposure Subscriptions
collection + individual document resource

### Context

Continuing task #106's UDR resource-type-breadth gap-closure (58 of free5GC's ~42+ real
`Nudr_DataRepository` resources closed as of ADR-0147). ADR-0122 had previously characterized
`ee-subscriptions`/`sdm-subscriptions` blanket as "confirmed genuinely deeply-nested" and left
both deferred without a real, individual YAML read of `ee-subscriptions` itself. This pass reads
it directly: `/subscription-data/{ueId}/context-data/ee-subscriptions` (real spec operations
`Queryeesubscriptions`/`CreateEeSubscriptions`, a collection GET+POST) and
`/subscription-data/{ueId}/context-data/ee-subscriptions/{subsId}` (real spec operations
`QueryeeSubscription`/`UpdateEesubscriptions`/`ModifyEesubscription`/`RemoveeeSubscriptions`, the
individual document's GET+PUT+PATCH+DELETE), schema `EeSubscription` -- required
`callbackReference` (Uri) + `monitoringConfigurations` (opaque JSON), plus a real dozen-plus
optional fields.

The correction: the collection GET's own `event-types`/`nf-identifiers` query parameters are real
`style: form, explode: false` arrays, but on direct read neither is `required: true` (unlike
`5g-vn-groups/internal`'s `internal-group-ids` or `nidd-authorization-data`'s own complex
parameter) -- so this is the same real, disclosed "optional filter this project doesn't honor"
class already used for `rangingsl-privacy-data`'s own `fields` parameter (ADR-0135), not the
genuinely-blocked required-array-param class. The resource itself is buildable; it just needed an
individual read rather than a blanket bundled deferral.

Three real, new shapes found and disclosed while implementing, none seen before in this project's
UDR work:
1. `subsId` is genuinely server-generated by the UDR, not client-supplied -- confirmed by the
   spec's own `Location` header format documentation
   (`{apiRoot}/.../ee-subscriptions/{subsId}`) and the absence of `subsId` as a request-body or
   path field on the `POST`. Generated via `sbi_core::generate_uuid_v4()`, the same generator this
   project's own NF instance IDs already use.
2. `UpdateEesubscriptions` (PUT) is genuinely update-only, never create -- the real spec's own
   `404` response for this operation explicitly says "update of non-existing resource is
   rejected", a real, disclosed departure from every other single-key PUT resource this project
   has closed so far (all of which are either create-capable via PUT or upsert-capable).
3. A real collection-GET + individual-document CRUD pair together, backed by one composite-key
   table -- a genuinely different shape from this project's prior "collection-of-columns"
   (`provisioned-data`) or "single-key document" precedents.

### Implementation

- `nfs/udr/schema.postgres.sql`: new `udr_ee_subscriptions` table (`ue_id`, `subs_id` composite
  PK, `data` JSONB).
- `nfs/udr/src/stores.hpp`/`.cpp`: new `EeSubscriptionsStore` class (`create`/`get`/`list`/
  `update`/`apply_patch`/`remove`). `create()` takes the caller-generated `subs_id` as a parameter
  (generation lives in `main.cpp`, reusing the existing `sbi_core::generate_uuid_v4()` include,
  rather than adding a new include to `stores.cpp`). `update()` returns `bool` (affected-rows
  based) rather than upserting, matching the real update-only PUT semantics.
- `nfs/udr/src/main.cpp`: store construction, five new OTel counters (create, list, get, write
  [PUT+PATCH share it], delete), and six new routes: `GET`/`POST` on the collection path, `GET`/
  `PUT`/`PATCH`/`DELETE` on the individual path. The `POST` response's `Location` header follows
  this project's own established convention (seen already in `smf-registrations`,
  `nfs/udr/src/main.cpp:1401`) of appending the new child segment to the collection path pattern
  without resolving `{ueId}`, rather than inventing a new, inconsistent fully-resolved-URL
  convention.

### Live verification (real, live PostgreSQL, not self-consistency)

Real curl sequence against a running `udr` process (freshly built, freshly started, registered
with a freshly started `nrf`) backed by real PostgreSQL, SUPI `imsi-999700000000011`:

- `GET` the collection before any `POST` -> real `200` with an empty array.
- `POST` with `{"callbackReference":"https://af.example.com/callback",
  "monitoringConfigurations":{"config1":{"eventType":"LOCATION_REPORTING"}}}` -> real `201`, a
  real, freshly-generated UUID v4 `subsId` in the `Location` header (confirmed genuinely random
  and well-formed), body echoed back.
- `GET` the individual resource by that `subsId` -> real `200` with the same body; `GET` the
  collection -> real `200` with a one-element array containing it.
- `PUT` an update to the same `subsId` -> real `204`; `GET` after -> real `200` reflecting the new
  `callbackReference`.
- `PUT` to a nonexistent `subsId` -> real `404`, confirming update-only semantics (no
  create-via-PUT).
- `PATCH` with a real RFC 6902 `[{"op":"replace","path":"/callbackReference","value":"..."}]` ->
  real `204`; `GET` after -> real `200` reflecting the patched value.
- Direct `psql SELECT` against `udr_ee_subscriptions` independently confirmed the single row
  (composite key `(imsi-999700000000011, <the generated subsId>)`) matched curl's response
  exactly at this point.
- `DELETE` -> real `204`; `GET` the individual resource after -> real `404`; `GET` the collection
  after -> real `200` with an empty array again.

### Testing and verification

A real `-Wsign-conversion` warning (`pqxx::result::size_type` is `int`, `std::vector::size_type`
is unsigned) surfaced in `EeSubscriptionsStore::list`'s own `reserve()` call on the first build --
fixed with an explicit `static_cast<std::size_t>`, disclosed rather than left in place. `udr`
built clean (zero warnings) both before and after `clang-format-18` (reformat added no diff beyond
what was newly written). Full `conformance_tests` (excluding the two disclosed pre-existing flaky
tests): 325/325 pass, zero regressions.

### What this ADR does NOT include

No NF's own existing logic calls these new routes (same disclosed "surface first, wire consumers
later" precedent already used repeatedly for UDR's own resource-breadth gap-closure). Real,
disclosed scope narrowing: only the collection + individual document are implemented -- the
deeper `amf-subscriptions`/`smf-subscriptions`/`hss-subscriptions` nested sub-collections under
each `subsId` (real, separate resources with their own paths) remain genuinely deferred, not
built. `sdm-subscriptions` (a real, separate resource ADR-0122 bundled alongside
`ee-subscriptions` in its own original deferral) was NOT re-surveyed in this pass and also remains
deferred -- this ADR corrects and closes `ee-subscriptions` specifically, not the whole bundle.
This closes UDR resource #59 of free5GC's ~42+ real `Nudr_DataRepository` resources. Task #106
remains open: `group-data`'s remaining genuinely-blocked resources, bare
`/subscription-data/{ueId}`/`{ueId}/context-data`, `ee-subscriptions`'s own nested
sub-collections, `sdm-subscriptions`, and the other genuinely deferred subsystems
(`subs-to-notify`, `pdtq-data`, `mbs-session-pol-data`, `nidd-authorization-data`,
`service-specific-authorization-data/{serviceType}`, `Nudr_GroupIDmap`'s own `/nf-group-ids`)
remain real, open, disclosed gaps.
