## ADR-0466: UPF container packaging: Dockerfile, Compose service and Helm chart

**Date:** 2026-10-07. **Status:** Accepted; the Helm chart is linted and rendered, the Compose file parses, the image was first built and the container first run on 2026-10-09 (see **First container run** below). Open: the advertised-address gap below.

**Context.** The UPF was the one built NF with no Dockerfile, Compose entry or Helm chart, so Definition-of-Done item 7 was open for it (found by the 2026-10-06 docs sweep: Compose had 26 NF services, none of them `upf`).

**Decision:** (1) `deploy/docker/upf.Dockerfile` is derived from `smf.Dockerfile` (same builder stage, `--target upf`). Its runtime stage adds `libbpf1 libelf1 libcap2` (the three non-libc libraries `ldd nfs/upf/upf` shows) and `iproute2` (the datapath runs `ip link/addr/netns`), and copies `gtpu_decap.bpf.o` to the same absolute path it has in the build tree, because `GTPU_BPF_OBJ_PATH` is a compile-time absolute path. (2) The `upf` Compose service carries `../../config:/build/config:ro` from the start (ADR-0453, DoD item 7), `UPF_NRF_BASE_URL: https://nrf:7777` (the env name `nfs/upf/src/main.cpp` reads), the ports 7796/tcp, 8805/udp, 9471/tcp, and `cap_add: NET_ADMIN, SYS_ADMIN, DAC_OVERRIDE, BPF, PERFMON`. The first three are the capabilities `nfs/upf/src/datapath.cpp` documents it needs for `ip link`, `ip netns` and the netns bind-mount; BPF and PERFMON are added for loading XDP and were not tested. (3) `deploy/helm/upf` renders `config/upf.json` from `values.yaml` into a ConfigMap mounted at `/build/config/upf.json` (a chart cannot mount `../../config`); its values equal `config/upf.json` except `nrf_base_url`, which points at the in-cluster NRF.

**Disclosed gaps.** (a) **Advertised address: resolved by auto-detect (not yet exercised in a container).** The UPF used to register `127.0.0.1` with the NRF and use a loopback PFCP Node ID, so in a container the SMF would send PFCP to itself. Decision (user-directed): a new `advertised_ipv4` setting (env `UPF_ADVERTISED_IPV4`, default `auto` in `config/upf.json`). `auto` opens a UDP socket, `connect()`s toward the NRF host from `nrf_base_url` and reads `getsockname()` (nothing is sent), so the UPF advertises the address it really uses to reach the NRF; a literal IPv4 overrides; hostnames, empty and `0.0.0.0` are rejected because the SMF parses a literal (`make_address`). If detection fails the UPF exits at startup rather than falling back to loopback. Code: `nfs/upf/src/advertised_address.{hpp,cpp}`, 8 unit tests in `tests/integration/test_upf_advertised_address.cpp`. Rejected: a fixed-IP Compose network (does not help Helm, and hardcodes addressing); making the SMF resolve hostnames (changes another NF to work around this one). Limit: auto-detect advertises the interface towards the NRF, which is the right one only if the SMF reaches the UPF on that same network; a multi-homed deployment sets the literal. (b) The datapath is a lab veth/netns fixture (10.99.0.0/30), not an N3 interface to a gNB. (c) The image was not built and the container not started. The chart passes `helm lint` and renders (helm v4.3.0, the official tarball with its sha256 verified; the existing `smf` chart lints the same way) and the rendered ConfigMap parses to `config/upf.json` with only `nrf_base_url` changed; `docker compose config` accepts the Compose file. Nothing was applied to a cluster. (d) The chart provisions no PKI, like the other charts. (e) `BPF`/`PERFMON` as Compose `cap_add` names are unverified on a real Docker host.

**Rejected alternatives.** `privileged: true`: grants far more than the datapath documents needing. Baking `config/upf.json` into the image: the exact mistake ADR-0453 exists to prevent. Leaving UPF out until the address fix lands: DoD item 7 would stay open and the gap would stay invisible; shipping it with the gap written down is more honest.

**First container run (2026-10-09).** `docker build -f deploy/docker/upf.Dockerfile` completed (178 MB, no errors) and the container was started through Compose with `--no-build`, against the Compose NRF. Three real defects surfaced that no earlier check could see, each fixed or recorded: (1) the container exited 127: `libli_core.so` not found, because the UPF links li_core (its LI POI) and the Dockerfile copied only the binary. Fixed with the same three additions `amf.Dockerfile` carries (`libxml2`, `libli_core.so` at its build-tree RPATH, the ETSI X1 schemas and the 3GPP X1 extension schema). (2) The UPF then aborted with "failed to load TLS material (cert=/build/certs/upf/cert.pem)": `pki-init`'s NF list in docker-compose.yml had no `upf`. Fixed by adding it; a check of every Compose service that mounts `certs_data` against that list found no other missing NF (`nwdaf-mtlf` reads `certs/nwdaf/`, already issued). (3) Not fixed, still open: the lab datapath fails inside the container with `mount --make-shared /run/netns failed: Permission denied`, so the eBPF/XDP datapath does not start even with the `cap_add` list in the Compose file (NET_ADMIN, SYS_ADMIN, DAC_OVERRIDE, BPF, PERFMON). The UPF handles this as designed (logs it, keeps PFCP and SBI up). Which extra privilege or relaxed security profile the netns mount needs has not been determined, and is not guessed here. **Verified in the container:** the SBI server listens with TLS 1.3 + mTLS, the UPF registers with the NRF (HTTP 201, type UPF), PFCP listens on 8805/udp, and `advertised_ipv4: auto` picked the container's own address (172.19.0.17), which closes the "not yet exercised in a container" caveat of gap (a). **Not verified:** a PFCP association from a real SMF, the datapath, the Helm chart on a cluster. The containers were removed afterwards.

**Datapath mount failure: cause reproduced (2026-10-09), fix NOT applied.** In the container `ip netns add` fails with `mount --make-shared /run/netns failed: Permission denied` although `NET_ADMIN`, `SYS_ADMIN` and `DAC_OVERRIDE` are granted. Reproduced with `docker run --cap-add NET_ADMIN --cap-add SYS_ADMIN --cap-add DAC_OVERRIDE` on the UPF image: rc=1; the same command with `--security-opt apparmor=unconfined` succeeds (rc=0). Docker here reports `name=apparmor,profile=default`, so the cause is the runtime-default AppArmor profile denying `mount`, not a missing capability. Options, for the user to choose: (a) `apparmor=unconfined` for the UPF as a labelled lab setting (broad: removes AppArmor confinement for that container); (b) a custom AppArmor profile allowing only the needed mount (not written); (c) leave the datapath off in containers (current behaviour: the UPF serves PFCP and logs that the datapath was not started). Not tested on Kubernetes (the Helm chart's equivalent is `appArmorProfile`). No compose or Helm change was made.

**Decision on the datapath mount (user, 2026-10-09): option (b), a custom AppArmor profile.** Written as `deploy/apparmor/5gc-upf` (syntax-checked with `apparmor_parser -Q -K`; allows only the `ip netns add` mounts plus bpffs, keeps Docker-default-style /proc and /sys write denials), loaded by `scripts/apparmor/load-upf-profile.sh` (needs root), selected in Compose via `UPF_APPARMOR_PROFILE` (default `docker-default`, so nothing changes until the profile is loaded) and in Helm via `securityContext.appArmorProfile` (default RuntimeDefault). **NOT verified:** the profile was never loaded or run (no root in the session), so whether it is sufficient for the datapath is unknown; the first run must read `dmesg | grep DENIED` and add the exact missing rule, never a blanket `mount,`. Rejected: `apparmor=unconfined` (removes confinement entirely). The Helm `appArmorProfile` field requires Kubernetes 1.30+.
