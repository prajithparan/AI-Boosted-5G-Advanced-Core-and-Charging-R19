## ADR-0351: AVP names alongside the wire codes, and the CAP gap ADR-0346 left open

**Date:** 2026-09-12. **Status:** accepted. Unblocked by the user supplying TS 32.299 and RFC 4006.

Two things, because chasing the first one found the second.

### 1. The capability gap: `cap_attributes` was never called

ADR-0346 built `gy_attributes()` and `cap_attributes()` so that Gy and CAMEL traffic could be
scoped onto products, and recorded that this closed the "N40 only" gap. `gy_attributes` was wired
into `diameter_server.cpp`. **`cap_attributes` was wired into nothing.** Its only caller was its
own unit test.

So in the shipped binary every CAMEL call still passed no attributes at all and `charge_one_usage`
fell through to its empty-object default -- meaning the entire legacy voice estate could only ever
match an **unscoped** offering. The builder existed, the test passed, the ADR claimed the capability,
and no CAP request ever reached the code.

This is the fourth instance of the same failure shape in this subsystem: `pDUSessionChargingInformation`
capitalised wrong and silently ignored (ADR-0343), `charging_information_type` detected then dropped
before the insert (ADR-0349), the column/value count mismatch that lost whole batches while the
generator reported zero failures (ADR-0349). **A builder with no caller, a field with no reader, a
value with no column -- each passes its own test and each is invisible until someone follows the
value all the way to where it is consumed.** The check that finds these is not a unit test; it is
grepping for the call site.

Fixed: `cap_server.cpp` now builds the attributes at InitialDP and passes them at both charge sites.
The attributes are remembered on the dialogue alongside `current_rating_group` and for the same
reason ADR-0298 gave -- an ApplyChargingReport carries no serviceKey or party numbers, so a renewal
rebuilding them from the report alone would rate the second period against a different scope than
the first.

`cap_attributes` now takes the parameters in the types `cap_core` actually decodes them into. The
party numbers are **opaque octets** and are emitted as hex, not as digits: this repository has no
decoder for `CalledPartyNumber`'s nature-of-address + TBCD layout, and digits would be a guess that
a reader would take for an E.164 number and never re-check.

#### The root cause: no test asserts what a CAP charge is rated *against*

A CAP dialogue test does exist -- `ChfProtocolCeilings.Ss7InitialDpIsServedWhenNoCeilingIsConfigured`
drives a real InitialDP over M3UA into a spawned CHF. What it asserts is **admission**: that the
message was served rather than shed. Nothing asserts what the resulting charge was *scoped by*.

So `cap_attributes` had a unit test for what it returns, and the CAP path had an integration test
for whether messages get through -- and the gap between them, *is the returned value ever passed to
the rating engine*, was tested by neither. A builder with no caller sits exactly in that gap.

What is verified now: the unit behaviour of `cap_attributes`, and that the call compiles into
`cap_server.cpp` at both charge sites. What is **not**: that a CAMEL call actually rates against a
scoped offering end-to-end.

The test to close it extends the existing ceilings harness (or follows
`tests/integration/test_udm_map_server.cpp`, ADR-0299) with a scoped offering and an assertion on
the RatingDecision the InitialDP produces. It is **not** written here for a scheduling reason rather
than a judgement: it spawns a CHF plus product-catalog and balance-management, and the 2M-CDR soak
currently owns ports 7884-7891, 7785 and 7786. A test that cannot be run cannot be trusted, so it is
queued rather than written blind. **Tracked as the immediate follow-up once the soak completes.**

### 2. AVP names, from the supplied spec, cross-checked three ways

ADR-0346 keyed attributes by wire code (`Gy.avp.432`) and committed: *"If TS 32.299 is supplied,
friendly names go alongside the codes -- never instead of them."* It is supplied, so they are.

`diameter_core::avp_name(vendor_id, code)` carries **613 names**, generated by
`tools/avp-dictionary/extract_avp_names.py` from Table 7.1.0.1 (IETF AVPs, vendor 0) and Table
7.2.0.1 (3GPP AVPs, vendor 10415) of the real ETSI TS 132 299 V19.0.0 (2025-10) at
`specs/TS_32-299.pdf`.

**Citation class:** a real 3GPP spec PDF -- the same class as `dictionary.hpp`'s `Sy` block and
*not* the freeDiameter C source its base/DCC constants cite. Disclosed, not quietly equated.

The extraction is column-aligned text from a PDF, which is exactly the kind of input that fails
silently: a shifted column gives a plausible name against the wrong code, and an operator would
scope a tariff onto `Rating-Group` believing they scoped `Service-Identifier`. So the generator
refuses to emit unless three derivations agree:

1. **The summary tables** -- fragile, parsed name-then-first-integer rather than by fixed column,
   because the columns genuinely shift and page headers interleave mid-table.
2. **That same document's own prose** -- `The <Name> AVP (AVP code <N>)`, one line, immune to column
   drift. 398 citations; **371 names carried by both sources, all agreeing.**
3. **freeDiameter's vendored C source** -- a different citation class with no common ancestry in
   this repository. 64 names overlap; **all 64 agree.**
4. **22 codes read by hand** out of the supplied material before the generator existed, asserted in
   `test_protocol_attributes.cpp` so a future respin cannot quietly lose them.

### Two bugs the cross-checks did NOT catch, and what did

Worth recording, because both produced a full, plausible, internally-consistent table that passed
every automated check above:

- **The generator first carried hardcoded `grep`-derived line offsets.** Python's `str.splitlines()`
  also splits on the form-feed page separators `pdftotext` emits, so its line numbers ran ~1 per page
  ahead of every other tool's -- about 94 lines by the start of clause 7. The regions were therefore
  read from the wrong place, and the result was 502 names with **zero reported conflicts**, because
  the rows it happened to read were genuinely valid rows, just the wrong ones. The cross-checks
  guard against misalignment *within* a row; nothing guarded against reading the wrong *region*.
  Fixed by locating all four regions from their own real headings at run time and refusing to run if
  an anchor is missing, duplicated, or out of order -- and by stripping form feeds so the numbering
  matches every other tool.
- **The name pattern required a leading letter.** AVP names may start with a digit, and the entire
  `3GPP-*` family does -- `3GPP-RAT-Type`, `3GPP-IMSI`, `3GPP-Charging-Id`,
  `3GPP-User-Location-Info`. All of them were dropped, silently, in both the table and the prose
  parse; the table still built and every cross-check still passed, because a name absent from *both*
  sources contradicts nothing. This is the family a Gy scope most often needs.

What caught both was **spot-checking the output against values known independently beforehand** --
not the automated agreement checks, which can only compare what was actually read. Hence check 4.

### What the cross-check actually caught

Not hypothetical. TS 32.299 V19.0.0 contradicts itself in three places, and the rule *"the
normative summary table wins, every divergence is reported"* was chosen because the table is right
in each:

- Clause **7.2.111Ab** is headed `Monitoring-UE-HPLMN-Identifier AVP` but its body sentence reads
  *"The Monitoring-UE-VPLMN-Identifier AVP (AVP code 3431)"* -- a copy-paste error. Table 7.2.0.1
  correctly lists 3431 as `Monitoring-UE-HPLMN-Identifier`, and 3433 as the VPLMN one.
- Clause 7.2 prose gives `Time-First-Reception` as code **3456**, but 3456 is
  `Proximity-Cancellation-Timestamp` in both the table *and* its own prose clause. The table lists
  `Time-First-Reception` as **3466**.
- Nine AVPs are spelled two ways for one code (`Service-Id`/`Service-ID`,
  `RAN-End-Time`/`RAN-End-Timestamp`, `ProSe-Direct-`/`ProSe-Direst-Discovery-Model`). The table
  spelling is kept; the code is agreed by both sources, so only the spelling differs.

### Disclosed gaps

- **6 AVP names are not emitted.** 8 names wrap across lines in the table; 2 of those are recovered
  from their prose clause, leaving 6 with no name (they are defined in other specs, so TS 32.299
  carries no prose for them). Joining wrapped rows would mean guessing where the name ends and the
  flag columns begin. The numeric key still carries all 6 -- which is the entire point of emitting
  names *alongside* rather than *instead*.
- Names are for scoping only. This dictionary names the AVP; it does not give its **type**, so
  values are still offered as both string and `u32` exactly as before.
- Clauses 7.3/7.4/7.5 (3GPP2, ETSI, oneM2M vendor spaces) are deliberately not extracted.

### Why this is safe to ship

The numeric key is always emitted, and `charging_scope_matches` (ADR-0303) looks up only the keys
an offering's own `chargingScope` names. Extra keys therefore cannot change which offerings already
matched -- a wrong name could only ever fail to match, never silently match the wrong thing. The
attributes map is not persisted wholesale either: `write_converged_charging_cdr` reads four named
keys from it and `input_snapshot` does not carry it at all, so naming adds no storage cost.

Each AVP gets exactly **two** paths, one fully numeric and one named, carried as two prefixes
through the recursion. Branching per nesting level instead would give a depth-3 grouped AVP eight
spellings of the same value for no extra reach.

### Rejected

- **Names instead of codes.** A code absent from the dictionary would become unscopable, and a
  vendor extension or a future release would be unreachable until someone updated a table.
- **A runtime-loaded JSON dictionary in `config/`.** This is spec reference data, not deployment
  configuration; the no-hardcoded-config rule is about DB URLs and ports. `dictionary.hpp` is the
  established precedent, and a source table is a binary search rather than a parse per start-up.
- **Hand-typing 502 constants with per-constant citations**, as `dictionary.hpp` does for its ~60.
  At this size hand-transcription is itself the likeliest source of a wrong name. The generator plus
  its three cross-checks is the stronger guarantee, and it is re-runnable against a future revision.
